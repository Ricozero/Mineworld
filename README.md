# Mineworld

Mineworld 是一个使用 C++20 开发的多人在线体素游戏实验项目

## 已实现功能

- 基于 16×16×16 区块的体素世界和基础地形生成
- 基于 EnTT 的玩家、机器人和物理实体
- 支持本地游戏、远程客户端和专用服务器
- 基于 Asio、UDP 和 KCP 的可靠网络通信
- 使用 FlatBuffers 序列化握手、输入、实体和区块数据
- 基于 bgfx、GLFW 和 ImGui 的渲染及界面
- 客户端连接状态、超时处理和返回主菜单
- 初始核心区块加载及 ClientReady 流程
- 集成 Tracy 性能分析

## 构建

项目使用 C++20、CMake、Ninja 和 vcpkg，并已在 MSVC 下测试通过

```console
cmake --build build --config Debug
```

可执行文件和运行配置生成到 `bin/`。

## 运行

启动客户端：

```console
bin/mineworld.exe [client]
```

启动专用服务器：

```console
bin/mineworld.exe server
```

## 开发环境

- 使用 clangd 提供代码分析和格式化，需要手动安装
- 已关闭 VSCode cpptools 的 IntelliSense，`c_cpp_properties.json` 不再使用
- FlatBuffers 生成文件位于 `build/src/generated/`，不要直接修改
- 使用 Tracy 查看客户端帧、服务端 tick 和自定义性能指标

## 计划

### 当前

#### 第一阶段：服务端区块同步预算

1. 每个会话继续使用 cachedVisibleChunks、coreChunks、newlyVisibleChunks 和 pendingChunkUpdates 维护独立发送状态
2. pendingChunkUpdates 按 chunkPos 去重，使同坐标最后一次 Upsert 或 Unload 覆盖尚未发送的旧操作
3. 发送优先级依次为 Loading 核心区块、Unload、新进入视距区块和其他可见区块，同类按玩家距离排序
4. 新进入视距的发送优先级保持到消息实际发送或被同坐标后续操作覆盖，不能在下一 tick 自动降级
5. 每 tick 对每个会话同时限制消息数量和序列化后字节数，达到任一预算后保留剩余消息
6. 区块发送调度从 EntitySnapshot 发送时机中分离，区块积压不能阻塞实体同步和客户端输入
7. 为待发送数量、每 tick 发送消息数、发送字节数和预算耗尽次数增加 Profiler 数据

完成标准：核心区块不会被普通区块阻塞，过期 Upsert 和 Unload 能在发送前正确覆盖，单个会话的区块积压不会形成突发网络流量或影响其他同步消息。

#### 第二阶段：客户端区块生命周期和网格调度

1. 明确每个区块的数据状态和网格状态，统一管理待加载、已加载、网格待重建、网格就绪和待卸载生命周期
2. 保持区块数据应用预算和网格重建预算相互独立，任何一侧积压都不能在单帧内无限处理
3. Loading 阶段继续优先应用和重建核心区块；Running 阶段优先处理新到达和距离玩家较近的区块
4. Unload 覆盖尚未应用的 Upsert，并取消该区块无效的待重建任务；相邻区块只保留一次必要的网格失效
5. 为待应用区块和待重建网格设置容量上限，溢出时优先保留核心区块、最后操作和最新 revision
6. 为应用耗时、网格构建耗时、队列长度、丢弃和覆盖次数增加 Profiler 数据，根据结果继续优化客户端热路径

完成标准：大量区块持续到达时客户端帧时间保持稳定，核心区块能够优先就绪，过期数据和无效网格任务不会形成长期积压。

#### 验证顺序

1. 核心区块不会被普通区块阻塞，过期 Upsert 和 Unload 能在发送前正确覆盖，单个会话的区块积压不会形成突发网络流量或影响其他同步消息。
2. 区块持续生成和发送时，实体同步与客户端输入仍能正常更新
3. 反复跨越视距边界，确认客户端正常执行 Unload 和 Upsert，服务端保留区内的区块不会卸载或重复生成
4. 两名玩家请求重叠区块，确认只生成和存储一份
5. 玩家断开后正确减少 requester，并在延迟结束后卸载区块
6. 生成队列积压时玩家离开，确认未开始的 Queued 区块被取消，已经失去需求的结果不会提交
7. 单玩家出生时，全部 3×3×3 核心区块完成后进入 Running
8. 大量区块持续到达时客户端帧时间保持稳定，核心区块能够优先就绪，过期数据和无效网格任务不会形成长期积压。
9. 为队列长度、生成耗时、提交耗时、发送字节数、客户端应用耗时和网格重建积压增加 Profiler 数据

### 架构

- 事件系统
- 输入系统
- Lua，Sol2，协程
- Handle资源管理系统热加载（音乐，音效，材质，贴图集，着色器，脚本）
- 永久区块
- 区块增量修改
- 服务器区块生成
  - 增加固定大小的工作线程池
  - 主线程负责计算需求、更新状态机、投递任务和提交完成结果
  - 工作线程只读取 chunkPos、generationId 和不可变世界生成参数，生成 ChunkData 并写入线程安全完成队列
  - 提交前校验区块状态、requesterCount 和 generationId，过期结果直接丢弃
  - 服务器关闭时停止接收任务，清空未开始任务，等待工作线程退出并丢弃无效结果
- 客户端区块生成
  - 热缓存+冷缓存，对于冷缓存，需要自身版本和相邻区块签名一致
  - 多线程网格构建
  - 状态机，分成数据状态和网格状态

- 控制、实体、必需区块和普通区块使用独立队列，按顺序发送，存在队头阻塞后再考虑 KCP 多通道
- 字节令牌桶限制区块进入 KCP 的速率，超过 KCP 高水位时暂停普通区块
- Snapshot 和输入都可能停止发送时，增加 KeepAlive
- 区块压缩，palette + bit packing，RLE，zstd/lz4
- 区块共享编码缓存，由容量上限和 LRU 策略回收
- 考虑公网：三次握手，NAT
- 增加服务器错误，当前handleHandshake和onClientHello等地方出错会等待超时
